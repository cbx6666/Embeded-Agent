# 嵌入式智能陪伴 Agent 需求文档

版本：V1  
阶段：总体需求定义

## 一、项目概述

### 1.1 项目名称

嵌入式智能陪伴 Agent

### 1.2 项目背景

随着边缘计算、语音交互、视觉识别和轻量化大模型技术的发展，具备本地感知、状态理解和主动交互能力的桌面型智能终端逐渐具备落地条件。针对学习、办公和个人桌面场景，传统智能设备通常只提供单一功能，例如计时、播放、提醒或简单语音问答，缺乏对用户状态、环境状态和任务进程的持续理解能力，难以形成真正具有陪伴感与主动性的交互体验。

本项目拟设计并实现一个运行在嵌入式设备上的智能陪伴 Agent。该系统以桌面学习与工作场景为主要应用背景，通过整合视觉、语音、环境感知、状态建模和任务管理能力，构建一个能够持续感知用户状态、理解当前情境、进行轻量决策并通过显示、语音和灯光等方式进行反馈的桌面式智能体。

### 1.3 项目目标

本项目的总体目标是构建一个面向桌面学习与工作场景的嵌入式智能陪伴终端，使系统具备以下能力：

1. 感知用户是否在场、是否专注、是否分心以及当前情绪状态。
2. 识别并记录用户的专注任务过程，实现学习监督与时间管理。
3. 感知环境信息，如光照、噪声、温湿度等，并在必要时进行提醒。
4. 支持语音或文本形式的人机交互，完成用户指令接收与系统反馈。
5. 通过显示屏、语音、灯光等方式进行多模态输出。
6. 对用户的状态变化、专注记录和交互历史进行统计与总结。
7. 在本地或边缘侧运行核心逻辑，保证系统具备一定实时性、连续性和独立性。

### 1.4 目标应用场景

本系统主要面向以下场景：

1. 学生桌面学习场景。
2. 个人办公桌面场景。
3. 需要专注监督与轻度情绪陪伴的个人场景。
4. 轻量环境提醒与时间管理场景。

## 二、系统定位

### 2.1 系统定位

本系统定位为一套运行在嵌入式平台上的桌面智能陪伴 Agent，而非单一功能模块。它不是单纯的计时器、语音助手或情绪识别程序，而是一个围绕“用户状态理解—情境判断—主动交互”闭环展开的综合系统。

### 2.2 核心价值

系统的核心价值体现在以下几个方面：

1. 从被动响应转向情境感知与适度主动交互。
2. 从单点功能转向围绕学习 / 工作陪伴的连续服务。
3. 将视觉、语音、环境和任务信息统一纳入状态建模过程。
4. 在嵌入式设备上实现本地化、连续化、低打扰的智能陪伴体验。

## 三、用户与使用场景

### 3.1 目标用户

1. 有学习监督需求的学生。
2. 有时间管理和状态提醒需求的办公用户。
3. 希望在桌面场景中获得轻量交互陪伴的普通用户。

### 3.2 典型用户故事

用户在桌前开始学习时，系统通过摄像头和传感器识别到用户已到场，并检测其坐姿和视线状态。系统切换到待命陪伴状态，当用户说出“开始专注 25 分钟”后，系统进入专注模式，屏幕显示专注计时信息，并开始计时。

在专注过程中，系统持续监测用户状态。如果检测到用户出现频繁走神、玩手机、离席或明显疲劳等情况，系统根据当前策略决定是否进行轻量提醒，例如通过柔和语音或屏幕提示提醒用户适当调整状态。

专注时间结束后，系统主动提醒用户休息，并记录本次专注时长、专注质量和相关状态数据。系统可在一定时间后生成当日专注统计或阶段性总结，为用户提供反馈。

## 四、总体功能需求

### 4.1 功能总览

系统总体上应包含以下功能模块：

1. 用户状态感知模块。
2. 专注监督与时间管理模块。
3. 情绪识别与关怀模块。
4. 环境感知与健康提醒模块。
5. 交互输入模块。
6. 交互输出模块。
7. 数据记录与统计模块。
8. Agent 决策与状态管理模块。
9. 系统运行与异常处理模块。

以下对各功能模块进行详细说明。

## 五、用户状态感知需求

### 5.1 在场状态检测

系统应具备用户在场状态检测能力，能够判断当前用户是否位于设备前方或在可交互范围内。

输入来源可包括：

1. 摄像头图像。
2. 距离感知或其他辅助传感器。
3. 后续可扩展的多源融合结果。

系统至少应支持以下状态：

1. `present`（在场）
2. `away`（离席）
3. `unknown`（未知）

### 5.2 注意力与专注状态检测

系统应具备对用户当前注意力状态的识别能力，用于支持专注监督和提醒决策。系统应能够初步区分以下状态：

1. `focused`（专注）
2. `distracted`（分心）
3. `idle`（空闲）

该识别可以基于以下线索实现：

1. 面部朝向。
2. 视线方向。
3. 姿态稳定性。
4. 是否频繁偏离桌面任务区域。
5. 后续可扩展的行为分类模型。

### 5.3 行为状态识别

系统应支持对与学习 / 工作相关的关键行为进行识别，用于辅助专注判断和主动提醒，例如：

1. 正常学习 / 工作。
2. 低头玩手机。
3. 长时间发呆。
4. 趴桌休息。
5. 长时间离开座位。

### 5.4 状态更新机制

用户状态感知结果应被统一写入系统状态中心，并为后续提醒决策、显示状态和数据统计提供输入。

## 六、专注监督与时间管理需求

### 6.1 专注模式启动

系统应支持用户主动启动专注模式。启动方式包括但不限于：

1. 语音指令。
2. 文本输入。
3. 屏幕交互。
4. 后续可扩展的按钮触发。

用户可指定专注时长，系统应在接收到有效启动指令后：

1. 切换系统运行模式。
2. 开始计时。
3. 显示当前专注状态。
4. 开始记录本次专注过程。

### 6.2 专注过程监测

专注过程中，系统应持续监测：

1. 当前已专注时长。
2. 当前剩余时长。
3. 用户注意力状态变化。
4. 中途离席情况。
5. 疲劳或情绪异常情况。

### 6.3 分心检测与提醒

当系统检测到用户在专注过程中出现明显分心行为时，应支持根据策略进行提醒。提醒方式可包括：

1. 屏幕提示。
2. 语音提醒。
3. 灯光变化。

系统应支持提醒冷却控制，避免短时间内频繁重复提醒。

### 6.4 专注结束处理

当专注倒计时结束，或用户主动结束专注模式时，系统应：

1. 结束计时。
2. 更新系统运行模式。
3. 输出结束提醒。
4. 记录本次专注会话。
5. 为统计分析模块提供数据。

### 6.5 时间管理能力

系统应支持基础时间管理功能，包括：

1. 倒计时启动与结束。
2. 专注时长记录。
3. 多次专注会话统计。
4. 后续可扩展休息阶段管理和番茄钟循环。

## 七、情绪识别与关怀需求

### 7.1 情绪状态识别

系统应具备基础情绪状态识别能力，用于辅助判断当前用户是否存在疲劳、紧张或积极状态。

系统至少支持以下情绪状态：

1. `neutral`（中性）
2. `tired`（疲劳）
3. `stressed`（压力较大）
4. `happy`（积极）

情绪识别可基于：

1. 面部表情。
2. 行为特征。
3. 语音特征。
4. 后续可扩展多模态融合结果。

### 7.2 情绪关怀提醒

当系统检测到用户长时间疲劳、压力较大或情绪低落时，应支持触发轻量关怀反馈，例如：

1. 休息建议。
2. 温和鼓励语。
3. 配合显示的情绪反馈信息。

### 7.3 低打扰约束

情绪相关提醒应服从系统低打扰原则，不得在短时间内多次触发；在用户明确处于高专注阶段或离席状态时，应适当降低主动输出频率。

## 八、环境感知与健康提醒需求

### 8.1 环境信息采集

系统应支持采集或接收以下环境信息：

1. 光照强度。
2. 噪声水平。
3. 温度。
4. 湿度。

### 8.2 环境状态分析

系统应能够根据当前环境信息判断环境是否适宜学习或工作，并在必要时给出提示。例如：

1. 光照过暗或过强。
2. 噪声过大。
3. 温度或湿度不适宜。

### 8.3 环境提醒策略

环境提醒应采用轻量提示方式，并支持与其他提醒一样的冷却与优先级控制，避免对正常专注过程造成过度干扰。

## 九、交互输入需求

### 9.1 文本输入

系统应支持通过文本形式接收用户输入，用于开发阶段调试和无语音环境下的功能验证。

### 9.2 语音输入

系统应支持后续接入语音输入链路，包括：

1. 唤醒。
2. 录音。
3. 语音识别。
4. 文本语义解析。

当前阶段可先以文本形式替代语音识别结果。

### 9.3 指令理解

系统应能够理解与本项目核心功能相关的基本意图，例如：

1. 开始专注。
2. 结束专注。
3. 查询状态。
4. 查询时间。
5. 请求总结。
6. 普通问候或陪伴式交流。

## 十、交互输出需求

### 10.1 显示输出

系统应支持通过显示屏呈现当前系统状态与交互内容，包括但不限于：

1. 待机状态。
2. 聆听状态。
3. 思考状态。
4. 播报状态。
5. 专注模式状态。
6. 简单文本提醒或结果展示。

### 10.2 语音输出

系统应支持通过语音合成输出系统反馈，包括：

1. 指令确认。
2. 过程提醒。
3. 专注结束提醒。
4. 简单关怀反馈。

### 10.3 灯光输出

系统应支持通过灯光或其他视觉信号表达系统状态，例如：

1. 待机。
2. 唤醒成功。
3. 正在思考。
4. 正在提醒。
5. 异常状态。

### 10.4 多模态输出协调

系统应支持根据当前模式和情境协调不同输出方式。例如：

1. 用户专注时优先使用轻量显示提示。
2. 需要明确提醒时结合语音与显示。
3. 用户离席时可减少主动语音输出。

## 十一、数据记录与统计需求

### 11.1 数据记录范围

系统应对以下信息进行记录：

1. 用户状态变化。
2. 专注会话信息。
3. 提醒触发记录。
4. 交互消息记录。
5. 环境状态变化。

### 11.2 统计分析能力

系统应支持基础统计分析，包括：

1. 专注次数统计。
2. 专注总时长统计。
3. 分心次数统计。
4. 简单状态变化统计。
5. 后续可扩展为日总结与阶段性总结。

### 11.3 结果展示

系统应支持以屏幕文本或其他方式展示统计结果，供用户查看当前专注情况和状态趋势。

## 十二、Agent 决策与状态管理需求

### 12.1 统一状态中心

系统应维护统一状态中心，用于保存用户状态、交互状态、专注状态、环境状态、提醒冷却状态和最近运行记忆。

### 12.2 事件驱动机制

系统内部应采用事件驱动方式组织运行流程。用户输入、状态更新、定时器变化和系统触发都应作为统一事件进入处理流程。

### 12.3 决策机制

系统应基于当前状态与事件，决定：

1. 是否需要输出提醒。
2. 是否需要切换显示状态。
3. 是否需要启动或停止计时。
4. 是否需要记录新的统计信息。
5. 是否需要进行语音或显示反馈。

### 12.4 低打扰策略

系统在设计上应遵循低打扰原则，避免在高频状态变化或高专注场景下重复触发提醒。

## 十三、系统运行与异常处理需求

### 13.1 连续运行能力

系统应支持持续运行，在用户正常使用过程中保持状态更新、事件处理和输出响应能力。

### 13.2 模块失效容忍

当某些感知模块暂时不可用时，系统仍应能够在降级模式下运行。例如：

1. 无视觉输入时仍可支持手动专注模式。
2. 无语音输入时仍可支持文本输入。
3. 无环境传感器时仍可运行其他核心功能。

### 13.3 异常状态提示

当系统检测到关键模块异常时，应能够进行适当提示或记录，但不应导致整个系统直接失效。

## 十四、非功能需求

### 14.1 实时性

对于用户输入响应、定时器更新和基础提醒，系统应具备较好的实时性，避免明显延迟影响交互体验。

### 14.2 稳定性

系统应支持较长时间连续运行，不因短时输入异常或单个模块状态异常导致整体崩溃。

### 14.3 可扩展性

系统设计应支持后续新增或替换以下模块：

1. 摄像头输入模块。
2. 语音输入输出模块。
3. 灯光控制模块。
4. 本地数据库。
5. 更复杂的策略模块。
6. 更强的模型推理模块。

### 14.4 可维护性

系统应采用模块化设计，保持输入、状态、决策、动作和输出之间边界清晰，以便团队并行开发和后续维护。

### 14.5 可测试性

系统应支持在无真实硬件条件下通过 mock 输入和日志输出进行开发与测试。

## 十五、当前阶段开发边界

### 15.1 当前阶段应优先实现的内容

1. 软件核心运行时。
2. 状态管理与事件驱动框架。
3. 文本输入交互。
4. 专注模式。
5. mock 用户状态输入。
6. 简单主动提醒。
7. 本地记录与统计基础能力。

### 15.2 当前阶段暂不优先实现的内容

1. 全量硬件联调。
2. 完整语音链路。
3. 完整视觉识别链路。
4. 复杂 UI。
5. 多 Agent 架构。
6. 完整长期记忆系统。

## 十六、总结

本项目的本质不是实现若干分散功能的堆叠，而是构建一个面向桌面学习 / 工作场景的嵌入式智能陪伴 Agent。系统的关键在于：持续感知用户与环境状态，围绕用户任务过程进行状态建模和情境判断，再以适度主动、低打扰的方式完成反馈。

因此，系统需求的核心不只是“能识别、能计时、能说话”，而是围绕以下闭环展开：

```text
感知
-> 状态理解
-> 决策
-> 多模态反馈
-> 数据记录与统计
```

当前阶段的工作重点应放在软件核心与整体架构打底，在此基础上逐步接入视觉、语音、环境传感器与显示控制，实现完整嵌入式智能陪伴终端。
